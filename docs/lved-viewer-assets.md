# LVEDVIEWER Embedded Assets

`LVEDVIEWER.exe` is not only a shell around the SQLCipher payload. It embeds a
large set of product-specific HTML/CSS resources and viewer scripts that define
how modern LogoVista dictionaries are searched, browsed, and rendered.

Private extraction output lives under:

```text
/home/shoui/Agents/CodexMax/LogoVista/reports/lved-viewer-assets-v1/
```

No extracted proprietary template, image, executable, or dictionary text is
committed to the repository.

## Viewer Protocols And Hooks

The embedded templates and global scripts use more protocol forms than the
current corpus content alone exposes:

| Protocol/hook | Meaning for our reader |
|---|---|
| `lved.dataid:<id>` | Normal entry navigation. |
| `lved.dataid.result:<id>?<code>` | Search-result iframe asks the host to update the detail pane. |
| `lved.info:<name>` | Info/HANREI/about/copyright page navigation. |
| `lved.media.*` / `lved.media.sound:` | Media/audio playback. The global detail script posts `mediaended` to the host. |
| `lved.pdf:` | PDF/image-page media display. |
| `lved.dict.<code>:` | Cross/product-specific dictionary hooks such as picture-dictionary pages. |
| `lved.addr<block>:<offset>` | Address-style navigation generated by advanced/template code. |
| `lved.findnum:` | Detail-page inner-search result count callback to the host. |
| `lved.select:` | Search-result dictionary selection state callback. |
| `lved.group.settings` | Search group settings UI callback. |
| `lved.bookmark:` | User bookmark state, not content navigation. |
| `lved.plugin:` | Product-specific action/search hook. |
| `lved.sql:` | Product-specific SQL/result refresh hook observed in NANMED/NMEDEJ templates. |

The global detail script also implements in-page search/highlighting:

- `startSearch()`
- `clearSearch()`
- `lved.findnum:<count>` callback
- `highLight(anchor)`
- `window.chrome.webview.postMessage(...)` for context menu, copy, and media
  completion events

The global search templates implement multi-dictionary/串刺し result behavior
with iframes and `postMessage`:

- one iframe per selected dictionary;
- parent/child focus movement for arrow-key navigation;
- `initialize`, `setHeight`, `dictchangeprev`, `dictchangenext`, `link`,
  `sortTitle`, and `sortDict` message commands;
- `lved.select:<true|false>?<code>` for enabling/disabling dictionary result
  panes.

For our reader, these should become host-app message types or internal router
events rather than literal webview escapes.

## Product-Specific Search Semantics

The viewer metadata confirms that `advanced*`, `filter`, and optional tables
are not one global feature. They are product-specific UI surfaces:

- HBHYAKKA `Html_Template_Advanced.html` builds a category tree, combines
  keyword, scope flags, and genre ids, then opens `lved.plugin:1.<key>.<scope>.<genre>`.
- NANMED20 `Html_Template_Joken.html` opens `lved.plugin:1.<word>`.
- NANMED20/NMEDEJ12 `Html_Template_Kwit.html` opens `lved.plugin:2.<word>` and
  also references `lved.sql:2:0:0:0:<id>` for result refresh.
- KOJIEN7 `Html_Template_Bunya.html` opens `lved.plugin:1...` category hooks;
  its `Html_Template_Yorei.html` uses `lved.plugin:2...` example hooks.
- DAIJIRN4/HBJITSU/SINJIGEN example templates also use `lved.plugin:2...`.
- SINJIGEN `Html_Template_Kanji.html` contains a multi-part
  `lved.plugin:-.-.-.-.-...` hook.

This means `advanced1`, `advanced2`, `advanced3`, `filter`, `joken`, `kwit`,
`sakuin`, `genre`, `bunya`, `exam`, `kanji`, and `binran` should be modeled as
named product providers with explicit UI metadata. Generic labels such as
“advanced search” are insufficient for an end-user reader.

## Product Plugins

.NET metadata shows every major product has concrete plugin classes such as:

```text
LvedViewer.Plugin.<PRODUCT>.LvDictDetailEngine
LvedViewer.Plugin.<PRODUCT>.LvDictSearchEngine
LvedViewer.Plugin.<PRODUCT>.LvDictPlugin
```

High-value product overrides include:

- `DoGetDetailViewData`
- `DoGetIndexHtmlData`
- `DoGetDetailHtmlScriptFromSearchResult`
- `DoGetPrevDetailViewData` / `DoGetNextDetailViewData`
- `DoGetDictSearchTypeDataList`
- `DoGetDictSearchResultViewData`
- `CreateSearchResultItems`
- `GetDictMenuControls`
- `AnalyzeUri`
- product-specific `UserControls.LvDictSearchControl`

These overrides are not just chrome. They define how product menus, search
controls, index pages, examples, kanji pages, PDF pages, and plugin hooks are
stitched together.

## Current Reader Implications

For the custom reader, the right boundary is:

1. Database providers expose core content, search rows, info rows, media rows,
   retained trees, and optional provider tables.
2. A product-renderer/profile layer selects extracted/reimplemented template
   semantics for:
   - detail pages;
   - index/title browsing;
   - info/HANREI pages;
   - tree navigation;
   - advanced/filter/product search panels;
   - PDF/image-page views;
   - example/kanji/category/keyword providers.
3. The frontend host implements `lved.*` routes as internal navigation and UI
   actions.

The extracted templates are useful as format evidence, but the reader should
not depend on shipping proprietary viewer assets. Reimplement the semantics and
use the extracted files as private parity references.
